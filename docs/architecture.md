# WorkBot: the architecture as built

WorkBot is the assistant and workflow engine for Fieldstone Supply's operations, finance and support teams, with a public chat for customers. This is the system at its final release, Day 40: what runs, where state lives, the models, how it is deployed and operated, the design choices and their tradeoffs, the numbers, and what would change next. Model ids and prices are those configured in `src/lib/providers.ts` on 2026-10-26.

The product is one Next.js app; the marketing site in `site/` is a second, static one. Model calls go through one of three paths: the AI SDK for the web routes, the actions, the agents and the workflows (`modelFor(task)`, routed and traced); the provider SDKs directly for the terminal session; and the Claude Agent SDK for the explainer pipeline. Inngest runs the document workflow as checkpointed steps, calling back into the app for each.

## Data

Everything is in one Postgres database, one idempotent schema in `src/lib/schema.ts`. Development and tests run on PGlite with its pgvector build; production needs the `vector` extension installed on its Postgres, which the schema's first statement enables. What is stored where, and why:

- **Requests** are the unit of work: title, body, team, priority, status. Every intake path ends in one: the form, the API, the voice line, a document, the approval workflow.
- **The knowledge base** is 52 Markdown files in `content/knowledge`, indexed into `chunks` by heading, with a full-text vector always and a 1,024-dimension embedding when Voyage is keyed. The files are the source of truth; the index rebuilds from them.
- **Per-person state** is small and erasable: `memories` by visitor cookie, forgotten from `/settings`.
- **Documents and media** keep their derived records, not their bytes, except the inbox, which keeps a document's bytes for the length of its workflow run: `documents` (the extracted record, confidence, the fields to review), `reports` (the analyst's report and findings), `recordings` (frame notes and a timeline). `sheets` keeps a spreadsheet's file for 30 days, with the columns and totals read from it, since every question reads the file again.
- **Tickets and contacts** are one shape each (`tickets`, `contacts`), mapped from every source with the provider's record in `raw` and the rules that fired in `applied`, refreshed by the pull, the webhook and the nightly read (`sync_log` says how far behind each left the copy); the writes made through the ticketing system are remembered by key (`filings`), so a write asked twice is made once. `cache` holds reads from outside per tenant, with every read's outcome in `cache_reads`.
- **Entities from descriptions** (`vendors`, `locations`): tables `pnpm generate` writes from `content/entities`, one per description, with the model, route and page beside them.
- **People and access**: `users` with a role, `keys` stored as hashes, `sessions` a key opens, `credentials` sealed with AES-256-GCM. Every table, these included, carries a tenant and a forced row-level security policy; the app queries as `workbot_app`.
- **Operations data**: `traces` (every model call: tenant, purpose, prompt version, tokens, cached tokens, dollars, latency, success or the error message; no prompt or reply content), `prompts` (versions and traffic shares), `notifications` (the outbox), `inbox` (the workflow's status per document).

Flows are short. A chat message: cookie to visitor, memories and a compacted history to the prompt, the model with tools, a reply streamed back, memories extracted after the response. A document: bytes to the inbox, an event to Inngest, steps that read the bytes back from the database, a request and a document at the end, a notification in the outbox. A text message: Twilio's signed webhook, an event to Inngest, the same turn the web takes from the conversation on the server, the reply through the outbox, Twilio's status back by callback. A question about a sheet: the stored file read into a DuckDB of its own, the model's SELECTs run against it, the answer back on the page with every query and its rows.

## Tradeoffs

- **Own agent loop over a framework.** The loop is small enough to read and test, and the course needed the mechanics visible. A framework would bring observability and resumability; Inngest supplies the latter where it matters, and the traces the former. The same agent built on 3 frameworks (`docs/frameworks.md`) confirmed the loop for the product and chose LangGraph.js for the first agent that must pause for a person and resume (D12).
- **One database over several stores.** Vectors, documents' records and operational data all sit in Postgres. Simpler to run and back up; a search-heavy product would move the index to a vector store with its own scaling.
- **The AI SDK's provider adapters over direct SDK calls everywhere.** The adapters cost some control over provider options (caching, effort) in exchange for one call shape, middleware and structured output across providers; each provider constrains output to the schema in its own way, and a schema feature one of them lacks shows up as a retry. The terminal keeps the direct path so the wire format stays in view.
- **Durable workflows for documents, plain requests for chat.** A chat turn is seconds; a document can wait days for a person. The split keeps the fast path simple and gives the slow path checkpoints.
- **In-house tracing over Langfuse.** A table and a page took a day and store no content; Langfuse would add sessions, scores and prompt management with a UI, at the price of an account and content leaving the database. The seam is one function per concern.
- **Browser speech over hosted speech.** No keys, works in Chrome, interruption handled; worse recognition than Deepgram, no audio transcripts for recordings. The interfaces are 2 methods each so the hosted services can take the seats.
- **Small model first.** Haiku reads documents, investigates tickets, writes the SQL for a sheet's questions and, since the table could not separate the 2 on the golden set, answers chat; Sonnet lays out pages and judges the evals. A document costs under a cent in model calls; the risk is quality on hard documents, which the confidence threshold and the reviewer catch.

## Reliability, as built and as missing

Built: a fallback model behind every task (the other size on the same provider), taken when a call fails with a status another model can take, and rehearsed with `OUTAGE`; step, dollar and time limits on every agent; Inngest's 3 retries per step and a failure handler that marks the document; a retry and a text fallback for the browser; words when embeddings are missing; idempotent filing (the request's creation is its own step); a public-address guard on every fetch; a rate limit on the chat; alerts on error rate and spend; the smoke evals as a gate on every pull request that touches a prompt, a tool, a model or an eval, in CI and in the fleet's queue, with the full suite nightly on the scoreboard (`docs/evals.md`).

Missing: a second provider in the chain, which needs its key and its column in the table; a daily dollar cap that turns the large-model fallback off, so a long outage or a loop cannot run up the bill (the on-call study's sharpest finding); a circuit breaker on a failing provider; a rate limit for the anonymous chat shared across instances; sign-in through the customer's identity provider; a person's confirmation on writes that leave the system; audio transcripts.

## Deployment and operations (Days 34 to 39)

- **Two images and a database.** The web tier is Next's standalone server; a tools image runs the realtime server and every operator command. They run on Vercel with Supabase, on Cloud Run with Cloud SQL, on any Kubernetes cluster, and on an Azure VM under systemd, from Terraform in `infra/` with one root per target and one state per environment ([hosting.md](hosting.md), [infrastructure.md](infrastructure.md)).
- **Releases are not applies.** Terraform makes each service once; a release migrates, waits for the new pods or revisions, runs the eval smoke suite and goes back on any failure. A broken tag was rolled back with the old pods serving.
- **Isolation by layer.** Three network tiers, no public database, every outbound call through an egress allowlist with a log, a KMS key per environment under the data and the secrets, and a customer kept apart in a project or namespace of its own ([isolation.md](isolation.md)).
- **What scale found.** An unbounded list, a scaler blind to CPU, and new replicas re-running the schema's DDL under traffic and deadlocking with inserts; the schema now runs once per version of it.
- **What a customer receives is tested.** The runbook, admin pages, incident runbooks, security documents and cost estimate were each given to someone in one role with one task; the most severe findings shipped the same day ([research.md](research.md)).
- **Found, measured, sold within the rules.** The public site is built for answer engines and checked in CI, citations are measured weekly, the target profile is code, and outreach carries its opt-out in every message ([growth.md](growth.md)).
- **Analytics as tested SQL.** Five metrics in SQL files with data tests, and an analyst agent that answers from them in SQL it shows ([analytics.md](analytics.md)).

## What would change next

1. **A spend cap with teeth.** A daily dollar limit that turns the large-model fallback off, so the most expensive failure is a slower answer, not a bill.
2. **A second provider in production.** The routing layer is ready; the column needs a key and an eval run, and then an outage costs latency instead of answers.
3. **Sign-in through the customer's identity provider,** with a second factor, and scoping by team or location for customers with several sites.
4. **The investigation as a job.** It still runs for minutes inside a request (Day 33); as a job with progress on the page it would survive a deploy.
5. **Eval sets per customer.** The sets are Fieldstone's, so Harbor Dental's release ran them as Fieldstone; its own policies and teams need cases of their own.
6. **Object storage for documents,** once the bytes outgrow the database, and the deployment's own data in the analytics instead of the seed.

## Audited against the principles (Day 26)

**As it is.** Two deployables: the app (Next.js, on Vercel) and the public site (`site/`, static, 140 lines). The app ships as two images, the web tier and a tools image for the realtime server and the operator's commands, and runs in containers on any cloud ([hosting.md](hosting.md)). One engine, Inngest, for the jobs, the document workflow and the crons, with a cap per sender. A realtime server for live calls' WebSockets, a container on its own, any number of instances sharing Postgres's NOTIFY. DuckDB in process, in memory, one database per question about a spreadsheet, closed after it. One database, Postgres with pgvector, 11 tables, JSONB where a record's shape is the model's to decide (documents' records, findings, a recording's scenes). One queue, Inngest's, with an outbox table for notifications. One observability stack, the `traces` table and its page. Two MCP servers for the CLIs, run from the repository, not deployed. Outside: the model providers, Chrome or a Playwright server, ffmpeg, and Brave, Voyage and PostHog when keyed. The layers are 3: route handlers and Server Actions, the functions of `src/lib`, and `query` with `$n` parameters in `db.ts`; nothing in between.

**Reading it.** Adding a field: 10 files. A provider down: the chain of Day 24 answers on the next model, and the sentence when none is left. One engineer locally: `pnpm dev` on an embedded Postgres and `pnpm inngest`, nothing else. Regenerated from configuration: the customer, the routes, the prompt versions; not the tools, which are code by choice.

**The 2 migrations.** The customer into configuration: `content/customer.json` names the company, what it is, its teams and what each files, where a document of each kind is filed, and the sections its customers may read; a Zod schema parses it at load and the prompts are functions of it. A new customer is a new file: 10 files touched became 1, 24 mentions of the name in code became 0, and the configured text is unchanged, so the evals did not move. The analyst's specialists into one agent: `pnpm compare:agents`, at the commit before the change (`1d73227`), ran the 17 golden answer cases through the analyst with its 2 specialists, through one agent with the same tools on the large model, and through one agent on the small model, each report scored by the judge with the case's criteria.

The comparison, its question settled, went with the commit that ran it.

**Carried into Weeks 7 and 8** (D15 and `brain/architecture/principles.md`): one deployable and the static site; Postgres, JSONB for what the model shapes; tools over retrieval; thin routes and plain functions; one agent unless an eval shows a second helps; the customer, the routes and the prompts as configuration; boring technology; and the 4 questions as the review of any design: how many places a field touches, what happens when a provider is down, whether one engineer runs it locally, what an agent can regenerate from configuration.
