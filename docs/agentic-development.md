# How we work with the CLIs

One repository policy, 3 terminal agents, a brain of notes they read, and a way of working that keeps a change reviewable. Written from one day of shipping with all 3 (Day 21); the comparisons are what happened, not a ranking.

## The policy, in files

| What         | Claude Code                                                                                                                | Codex CLI                                                         | OpenCode                                                                           |
| ------------ | -------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| Instructions | `CLAUDE.md` imports `AGENTS.md`, at the root and in each package                                                           | `AGENTS.md`, root and nested                                      | `AGENTS.md` at the root; the nested ones listed in `opencode.jsonc` `instructions` |
| MCP servers  | `.mcp.json`                                                                                                                | `.codex/config.toml`, `[mcp_servers.<name>]`                      | `opencode.jsonc`, `mcp`                                                            |
| Permissions  | `.claude/settings.json`, `permissions`                                                                                     | `.codex/config.toml`, `approval_policy` and `default_permissions` | `opencode.jsonc`, `permission`                                                     |
| Skills       | `.claude/skills/<name>/SKILL.md`                                                                                           | `[[skills.config]]` pointing at the same folders                  | `.opencode/commands/<name>.md`, written from the skills by `pnpm sync:commands`    |
| Checked by   | `scripts/agent-config.test.ts`: the 3 declare the same servers, every nested `AGENTS.md` is wired, every skill is in all 3 |

`AGENTS.md` is the source; the only copies are generated, and the test compares them. A new package gets an `AGENTS.md`, a `CLAUDE.md` of one line, and a line in `opencode.jsonc`; a new skill gets `pnpm sync:commands` and a `[[skills.config]]` entry; the test fails until it does.

## What each CLI enforces

The policy is the same sentence for all 3 (work in the tree, ask beyond it, never read `.env.local`); the configurations enforce unequal parts of it. A rule is something the CLI refuses or asks about on its own; an instruction is `AGENTS.md` asking the agent to behave, which nothing checks.

| ------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Enforced by a rule | `deny`: `Read(./.env.local)` and `Read(./.env*.local)` stop the file tools, Grep and Glob on a best-effort basis, and the shell commands Claude Code recognizes as reading a file (`cat`, `head`, `tail`, `sed`, `tee`) and redirections; `Bash(rm -rf:*)`. `allow`: the checks and read-only git, once the workspace has been trusted in an interactive session | A profile that extends `:workspace` and denies `.env`, `.env.local` and `.env.*.local` to every command the sandbox runs, and confines writes to the tree, system temp aside; `approval_policy = "on-request"`. ## Whose text an agent acts on

The issue form takes free text from anyone who can open an issue, and a pull request description is free text too. Issue and pull request text from non-collaborators is data, not instructions: an agent reads it to learn what is being asked and does not do what it tells the agent to do, such as running a command, reading a file, or changing a setting. A maintainer reads it first and either drops it or rewrites it as a brief under their own name.

An auto-approving run (`codex exec --approve-for-me`, `opencode run --auto`) answers its own prompts, so OpenCode's `bash: ask` stops nothing in it; what is left is the deny rules, and the table above shows how little each one denies. Auto-approving runs therefore take only briefs a maintainer wrote. Nothing in the configurations checks the author of an issue: this is a rule for the people who start the runs.

## The brain

`brain/` is what an agent reads before a task that touches product, architecture, the customer or style: an index, 5 notes, a `Reviewed` date each, and a retention rule (90 days, then archive; decisions superseded in place). It is read by path, not loaded into every prompt: the root `AGENTS.md` says where it is and asks for the note relied on to be cited. The budget rule: every session gets `AGENTS.md`; everything else the agent fetches when the task needs it.

## From issue to merged pull request

1. The issue is the brief: the form in `.github/ISSUE_TEMPLATE/task.yml` requires a goal and acceptance criteria, and asks for constraints, related paths and a session link. An issue without checkable criteria is sent back before any agent sees it.
2. Plan mode first for anything that touches more than one package; the plan goes in the pull request.
3. One pull request per unit of work, small; the template carries the brief (`Closes #`), the plan, the session per CLI used, and the checks.
4. The session is the handoff: a cloud session's link, or the local session's id, in the pull request, so the next person or agent can continue it rather than start over.
5. Review by reading the diff, running the tests and checking the brief's criteria one by one. The agent's summary is not the review.

Both auto-approving runs took an issue a maintainer wrote, which is the condition for them (see "Whose text an agent acts on"). Where each was faster or clearer: Codex for a closed brief with named files, fastest and quietest; OpenCode for a task that needs a check loop (write, run, fix) without a conversation, and for a second opinion from a different model family; Claude Code for the open-ended task, where plan mode, the docs tools and the long session pay for themselves. All 3 named `AGENTS.md`, the 5 servers and the 4 skills when probed; 3 things the probe taught: Claude Code ignores a project's `permissions.allow` until the workspace is trusted once interactively; OpenCode's `bash: ask` ends a non-interactive run at the first command it refuses, so a probe denies the shell for the run; and OpenCode's glob does not match under dot-directories, so it reads `.opencode/commands` as a directory instead.

## Checking a CLI picks the policy up

Ask it, with no write access: "the instruction files that apply here, the MCP servers configured for you, the skills or commands available to you". `claude -p --allowedTools "Read,Glob,Grep"`, `codex exec --sandbox read-only`, and `opencode run` with the shell denied for the run: `OPENCODE_CONFIG_CONTENT='{"permission":{"bash":"deny"}}'`. The answers name the same files, servers and skills, or the configuration is wrong for that CLI. The env rule has its own check, and it checks no more than the table above says is enforced: `opencode run` asked to read `.env.local` with its read tool answers with the rule, and says nothing of grep or the shell; `codex sandbox --permission-profile workbot -- cat .env.local` fails with "Operation not permitted". Codex applies the profile to a session only when no loaded config sets the older `sandbox_mode`, the user's `~/.codex/config.toml` included.

## Terminals and editors

One pane per agent, one browser, one notes app: cmux here, with the Chrome the agents drive and the course's pages beside it; Obsidian or any editor for the brain, which is plain Markdown. Session persistence matters more than the terminal: a session that survives a closed pane is a handoff that still works.
